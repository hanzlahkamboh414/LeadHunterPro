## 1. Vision & Permanent Goal (unchanged)

LeadHunter Pro is a **REAL, production-grade company-discovery platform**, not a
search-API client. Target domain: construction/contractor leads, **Texas-first**.
The business behind it (The Best Estimator LLC) sells construction estimation /
preconstruction services, so a *qualified lead* is:

> A company that is **provably in a buying window** AND has a **reachable
> decision-maker** who owns estimation/bidding decisions — never a company with
> a generic mailbox.

**V1 target:** 15–20 qualified Texas contractor leads, end-to-end, **zero budget /
free-keyless sources only**.

**Scale target (founder, 2026-08-19):** the prototype must be powerful enough to
find **~20,000 potential leads per day**. Read the unit carefully — *potential*,
not *qualified*: 20k is the volume the pipeline **screens**, while the qualified
count remains whatever survives the §3 gate. The gate is never relaxed to inflate
the number (CLAUDE.md §1/§12). Three architectural consequences follow, and they
are the reason this figure is recorded in the Vision rather than in a late stage:

1. **AI cost/throughput dominates.** ~20k screenings/day is far beyond any free
   flash tier, so the AI model and vendor **must** be swappable without a code
   change — delivered by **D7-B** (one `RouterProvider`, vendor named only in
   `backend/.env`). A local `Ollama` preset ships in `.env` precisely because
   self-hosting is the only unmetered way to serve this volume.
2. **Throughput is a Stage 2/5 concern, not Stage 1.** Correctness first: one
   qualified lead (**M3**) proves the gate; only then does volume mean anything.
   Multiplying a broken pipeline by 20,000 just produces 20,000 wrong answers.
3. **It hard-requires M6 (persistence), M9 (job runner), M20 (politeness) and
   M21 (cost control).** At this volume, re-crawling and re-paying for the same
   company is the dominant waste, and an unthrottled crawler gets IP-banned.

Second founder requirement, same brief: **"purana code re-write na karna pare,
bas naye feature add kar do"** — adding capability must mean *adding files*, not
editing working ones (Open/Closed). The AI registry (D7-B) is the first place
this is enforced structurally; new discovery sources already work this way via
`app/search_providers/registry.py`. Treat it as a standing design constraint for
every later milestone, not a one-off.

The "Execute" button must eventually perform REAL discovery (CLAUDE.md §10):

```
Search Internet → Find Companies → Visit Websites → Extract Company Information
   → Extract Decision Makers → Validate → Rank → Return Results
```

It must NEVER become: `Read Fixture JSON → Return Cached Companies`.
Fixtures exist ONLY as an emergency bridge — surfaced honestly as
`data_source="fixture"`, `bridge_mode=true`, with a `fallback_reason`.

**The one principle the whole architecture serves:** *every claim must have a
source.* That is why Evidence carries `source_url`, why justification must cite
evidence, why fixtures must confess, and why "fake live mode" is banned. The
product is **auditable leads**.

## 2. Architecture North Star (unchanged)

```
Discovery Engine
    ↓ Source Orchestrator          (SourceOrchestrator)
    ↓ Multiple Sources             (DirectoryCrawlSource · SearchProviderSource · FixtureSource · intent plugins)
    ↓ Crawler / Extractor          (HttpCrawler, session manager, website extractors)
    ↓ Validation + Ranking         (AcceptanceGate + CompanyScorer)
    ↓ Results
```

**Forbidden:** `Connector → Brave API → Results`. Search APIs are optional,
replaceable infrastructure — never the core (CLAUDE.md §3, §4, §8).
Layer direction: `api → services → engines → connectors → crawlers`. Dependencies
flow **down only**.

## 3. V1 Qualification Gate — Definition of a Qualified Lead (unchanged)

Deterministic gate in [lead_models.py](backend/app/engines/lead/lead_models.py)
(`Lead.qualification_gate`). A lead clears **ONLY** when every hard rule holds;
the gate reports EVERY missing requirement in `blocked_by`:

| # | Hard rule |
|---|---|
| 1 | **Verified company** — passed `AcceptanceGate` (`metadata["gate_accepted"]`) |
| 2 | **Named decision-maker** with `role_relevance=True` (owner, PM, estimator, procurement, operations, …) |
| 3 | **HARD** — a `person_bound` email (e.g. `f.last@company.com`). `info@`/`contact@` NEVER qualify |
| 4 | Phone is **OPTIONAL** — never blocks |
| 5 | **≥1 buying-intent evidence with a traceable `source_url`** — never invented evidence |
| 6 | `ai_confidence ≥ 90` backed by real evidence **+ a written justification citing that evidence** |

Tiers: **Email** `format` < `domain` (MX resolves) < `person_bound` (only
`person_bound` qualifies) · **Phone** `format` only · **Person identity**
`unverified` by design (`role_relevance` gates separately).

## 6. Sequencing Logic — Why This Order

| Question | Answer |
|---|---|
| **Why not the frontend first?** | 0 qualified leads = an empty UI; no leads API = nothing to call; a still-changing lead shape = guaranteed rework. You'd build it twice. |
| **Why is persistence (M6) before the API?** | The API's list/filter/history endpoints need a queryable store. Building them over JSON files means rewriting them. |
| **Why is the job runner (M9) before the leads router?** | Discovery takes minutes. Sync HTTP would time out and `asyncio.run()` inside a handler breaks the event loop (R3). The async model must exist first or the endpoints get designed wrong. |
| **Why auth (M12) before the UI?** | The moment a browser client exists, the API is exposed. Retro-fitting auth means touching every endpoint again. |
| **Why is the evidence viewer (M15) not optional?** | Auditability *is* the product. Without it this is just another lead list. |

## 7. Standing Workflow Rules (never violated)

1. **One increment at a time** — STOP after each phase, summarize, report changed files + test status, wait for explicit approval.
2. **Sequential manual verification** — ONE command at a time, wait for pasted output; never send Step N+1 before N passes. The checklist never restarts.
3. **Test invocation:** always `python -m pytest` **from `backend/`** (bare `pytest` fails).
4. **Ruff gate:** `Found 0 errors` on authored files; pre-existing findings on legacy files are out of scope by founder choice.
5. **Accuracy-first:** fixtures never primary; live-first; honest `EMPTY` vs `UNAVAILABLE`; never fabricate evidence; **a blocked verification never becomes a "PASS"**.
6. **No implementation while a verification is pending.**
7. **Never retry a blocked Bash/PowerShell command** — attempt once, queue a verification card.
8. **Never commit or run destructive git without explicit approval** (CLAUDE.md §13).
9. **Reuse before build** (§14) — search the repo for an existing implementation first.
10. **Zero budget / free-keyless only** for V1.
11. **Never stage** `backend/.env` (secrets) or `backend/output/` (real lead data).
12. **Never move the qualification gate to hit a target number.**
