1. ONE-LINE STATUS
--------------------------------------------------------------------------------
The back-end is a mature, well-architected, almost-fully-offline FastAPI package
(Sprint 2.x) with a real, honest, API-free live-discovery pipeline
(Planner -> DirectoryCrawlSource -> HTTPCrawler -> extractors -> gate -> rank ->
Lead qualification gate). The V1 "qualified lead" gate (lead_models.py) is
deterministic and correctly implemented. The critical gaps are:
environment/dependency gaps (aiohttp missing -> 5 test failures), a live-API key
imported at module import in a root `test_*.py` that breaks test collection,
duplicated/deprecated connector code (two parallel connector stacks), a layering
inversion (connector -> engine), missing project/tooling config
(no pyproject.toml/ruff.toml), and an undocumented/aspirational front-end that
does not exist. The front-end/desktop/docker/tools/assets/scripts top-level
directories are EMPTY.

3. EXECUTION FLOW
--------------------------------------------------------------------------------
User query:  GET /api/v1/discovery/companies?industry=Roofing&location=Dallas Texas
  -> discovery.py:discover_companies()  [sync def, module-level `engine =
     CompanyDiscoveryEngine()`]
  -> CompanyDiscoveryEngine.discover()
       step1 ConnectorManager.discover() -> list[ConnectorResult]
       step2 clean_companies()  (deduplicate by domain+name, fuzzy)
       step3 validate_companies()  (name validity + live HTTP HEAD)
  -> ConnectorManager.discover()
       -> ConnectorRegistry.get_enabled() -> [TexasProcurementConnector]
       -> TexasProcurementConnector.search()
            -> register_website_discovery()  (config-gated; no-op w/o BRAVE/SEARXNG)
            -> SourceOrchestrator.discover()
                 1) DirectoryCrawlSource   (priority 20)  REAL live crawl path
                 2) SearchProviderSource   (priority 50) empty here (no keys)
                 3) FixtureSource          (priority 999) emergency bridge
            -> WebsiteEnricher.enrich(...)  (fills city/state from company sites)
            -> Step-3 filter (state/city/keyword)
            -> AcceptanceGate (deterministic verification stack)
            -> _build_result + _attach_ai_intelligence (additive, gate-accepted only)
  -> validate_companies() runs a blocking requests.head() per result (see §8).

The "Execute" button (demo.py / the discovery API) therefore runs the REAL
pipeline: it always tries the API-free DirectoryCrawlSource first; only when
every live source is UNAVAILABLE/EMPTY does the FixtureSource bridge activate,
and the response is honestly tagged data_source="fixture", bridge_mode=true with a
fallback_reason. This matches CLAUDE.md §1/§5/§10.

4. ARCHITECTURE ASSESSMENT
--------------------------------------------------------------------------------
4.1 Stated rule (CLAUDE.md §4): api -> services -> engines -> connectors ->
     crawlers; dependencies flow DOWN only; AI is a leaf.
4.2 Reality / violations:
     - AI leaf-node rule: HONOURED at the package level. grep of app/ai/ shows it
       imports only app.ai.* and app.core.config (+ provider SDKs). It never
       imports engines/connectors/crawlers/services. Good. (engines/ai_engine.py
       imports app.ai.scorer/summarizer — correct direction: engines -> ai.)
     - Connector -> Engine inversion (MEDIUM/RISK): texas_procurement.py
       (backend/app/connectors/texas_procurement.py:583-647) imports INSIDE methods:
         from app.engines.verification.acceptance_gate import AcceptanceGate
         from app.engines.verification.identity_verifier import ...
         from app.engines.verification.industry_verifier import IndustryVerifier
         from app.engines.verification.location_verifier import LocationVerifier
         from app.engines.ai_engine import AIEngine            (line 647)
       A connector (lower layer) depends on engines/verification (higher layer),
       violating the "dependencies flow down only" rule. It is function-local and
       wrapped in try/except (so it doesn't crash discovery), but it IS a real
       architectural inversion and a circular-import risk that the function-local
       import masks. Flag for founder decision (§12).
     - Discovery package coupling: app/discovery/ imports engines, connectors
       (texas_procurement._parse_location), crawlers, search_providers — i.e. the
       "discovery" layer straddles multiple layers. Acceptable in practice (it is
       the composition/orchestration layer), but it is not a clean single layer.
     - No circular imports observed at import time in the offline test run.
4.3 Frozen units / public API: the project keeps completed units stable and uses
     dataclass `replace` to extend immutable ConnectorResult/CompanyDiscoveryResult
     (additive metadata) rather than mutating — e.g. texas_procurement.py:299
     `dataclasses.replace(result, metadata={...})`. Good discipline.
4.4 DI/seams: LeadPipeline (lead_pipeline.py:82-98) injects leadership,
     intent_plugins, scorer via Protocols — excellent for offline testing. The
     connector also accepts an injectable ai_engine for tests. Good.

6. DOES "REAL DISCOVERY" WORK?  (the core question)
--------------------------------------------------------------------------------
VERDICT: YES — the architecture and production code perform REAL, API-free
discovery; whether live data is returned at a given runtime depends on network
access to the seed hosts, NOT on the code.

Evidence:
- backend/app/engines/source_intelligence/source_models.py contains REAL public
  source URLs (not placeholders): agctexas.org, abctexas.org, thbaonline.com,
  enr.com/topspecialtycontractors, constructionconnect.com, thomasregister.com,
  osha.gov/data, sam.gov, cbiadia.org, etc. (Only the chamber entry deliberately
  has no URL — `texas_procurement._build_chamber_sources` refuses to fabricate
  one, per CLAUDE.md §12.)
- The live path is genuinely API-free (Blueprint §6 Phase 3):
  SourcePlanner -> DirectoryCrawlSource -> HTTPCrawler (robots/rate-limit/retry/
  cache) -> CompanyExtractor + ContractorClassifier -> SourceOrchestrator ->
  connector Step-3 filter -> AcceptanceGate -> rank. No Brave/Brave key needed.
- tests/discovery/test_no_keys_live_crawl.py PROVES the pipeline runs end-to-end
  with stubbed network and reports `data_source == "live"` (not fixture) and
  `directory_crawl: SUCCESS`, with the website-discovery plugin NOT registered
  (no live origin) and FixtureSource disabled in live mode.
- Honest source semantics: UNAVAILABLE (could not reach) != EMPTY (looked, found
  none) != SUCCESS. Fixtures only activate as the LAST source (priority 999) and
  are tagged data_source="fixture", bridge_mode=true, fallback_reason="..."
  (source_orchestrator.py:181-198; texas_procurement.search re-labels to
  "fixture" if live survivors drop out at the Step-3 filter — texas_procurement.py:333-350).

Runtime caveat: in THIS sandbox, directory_crawl will likely return UNAVAILABLE
(DNS to seed hosts blocked) and the run falls back to the fixture bridge — which
is EXACTLY the honest behaviour the project was redesigned to avoid hiding
(CLAUDE.md §1/§5). The `data_source`/`bridge_mode`/`fallback_reason` metadata
tells the operator precisely what happened.
